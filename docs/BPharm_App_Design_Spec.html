No-Code Product Design Specification · Confidential Draft

PharmaPath — B.Pharm Exam Companion

A complete 8-semester (Sem 1 → Sem 8) exam-prep app for B.Pharmacy students of Rajasthan University of Health Sciences (RUHS), built for Hindi-medium students who need complex pharmacy concepts in simple, point-wise, bilingual (English + Hinglish) format.

Why this split works on no-code

  • Auth: Glide Sign-In, Bubble native auth, or Supabase Auth — all no-code.

SECTION 5

Bilingual System (English ⇄ Hinglish ⇄ Hindi)

The toggle must be instant and cost-free for the user. Design rule: every content row stores all languages at creation time — the toggle is a pure client-side render switch, never a live AI call.

5.1 Storage strategy

Column (in notes table)FormatContent
en_pointsJSON array of stringsSimple English, 1 point = 1 line, ≤ 12 points
hinglish_pointsJSON array of stringsRoman-script Hindi with English medical terms: "Ye bacteria ke protein synthesis ko rokta hai"
hindi_pointsJSON array (optional)Devanagari Hindi (added progressively)
flowchart_jsonJSONSteps carry text_en + text_hinglish per step
glossary_termJSONHard terms auto-linked: "ribosome → राइबोसोम (protein banane wali machine)"

5.2 Hinglish writing rules (content QA standard)

  • Keep the medical word in English, explain around it: "Tetracycline 30S subunit se bind hota hai" — never transliterate jargon.
  • Short sentences, exam-ready verbs: "Ye drug bacteriostatic hai = bacteria ko marta nahi, sirf badhne se rokta hai."
  • One idea per point — same structure as English so switching languages maps 1:1 (point index n ↔ point index n).
  • Mnemonic hooks: "30S = 30 = teen-zero → 'teeno' proteins band" style memory aids are allowed and encouraged.

5.3 Glossary (the "complex jargon → simple words" layer)

Each hard term in a note gets a tooltip from the glossary table — one tap explains it in simple language without breaking reading flow:

TermSimple EnglishHinglish
BacteriostaticStops bacteria from multiplying; does not kill them directlyBacteria ko badhne se rokta hai, seedha marta nahi
Aminoacyl-tRNAThe "delivery truck" that brings amino acids to the ribosomeAmino acid ko ribosome tak pahunchane wali gaadi
PharmacokineticsWhat the body does to the drug (ADME)Body drug ke saath kya karti hai (ADME)
SporogonyMultiplication of the malaria parasite inside the mosquitoMalaria ke parasite ka mosquito ke andar multiplication

5.4 AI fallback translation (for scanner-generated content)

  1. Scanner generates en_points for an extracted item.
  2. Same AI call also returns hinglish_points (one call, both outputs — near-zero extra cost).
  3. Result is cached in the notes row → future reads are instant.
  4. If a user needs Hindi (Devanagari), a background job translates en_points → hindi_points in bulk nightly (batch API, cheapest model), flagging rows as hi_ready.
Result: the toggle (top bar, global) switches users.language_pref; every list/detail screen re-renders from the matching column. Zero API latency, works offline.
SECTION 6

Smart Syllabus / Screenshot Scanner — Full Design

The hero feature. It must obey one iron rule: only items physically present in the image get notes — nothing assumed, nothing invented. This is enforced at three levels: (1) the extraction prompt, (2) the per-item generation prompt, (3) a post-generation validation step that deletes anything not in the image list. A single prompt is not enough — the validation step is what makes the rule reliable.

6.1 End-to-end flow

User uploads image
→
Pre-process (rotate/crop/contrast)
→
AI Vision: extract items ONLY
→
Show checklist to user
→
Generate notes per selected item
→
Validation pass
→
Save + display

6.2 Step-by-step logic

#StepWhat happens
1UploadImage stored (scanner_sessions.image_url); user picks source type: Syllabus | Question paper | Drug list. Type changes the extraction prompt slightly (units/topics vs. questions vs. drug names).
2Pre-processClient-side contrast boost + optional manual crop (blurry phone photos of printed syllabus are the #1 failure mode — a simple "Enhance" filter cuts OCR errors massively).
3Extract (AI Vision call #1)Image → OpenAI gpt-4o-mini with the Strict Extraction System Prompt (below). Output = JSON array of items only. Nothing else is generated at this stage.
4User confirmationChecklist screen (S11): user can uncheck items, fix typos, add one manual item from the image if OCR garbled a word (optional; default = strict).
5Match libraryEach item fuzzy-matched against drugs / notes tables. Hits → reuse curated content (free, fast, accurate). Misses → go to step 6.
6Generate (AI call #2 per item)Point-wise bilingual notes with the Per-Item Generation Prompt (below). Runs in parallel (batch), max 10 items per session to control cost.
7Validation pass (the strict guard)Auto-check: every generated note's title must exist in the extracted item list exactly or by fuzzy match. Any note whose title is not in the image list → deleted/blocked. A system log row records the check ("item X → kept", "item Y → rejected: not in image").
8Save & showNotes saved to notes (linked to scan_items + scanner_sessions), user opens them in S8/S9; also saved in "My Scans" for revision.

6.3 The Strict System Prompts (copy-paste ready)

Prompt A — Strict Extraction (OCR + whitelist)

# SYSTEM PROMPT (send as "system" role, image in "user" role)
You are a STRICT pharmacy syllabus/drug-list OCR assistant.

RULES (mandatory):
1. Extract ONLY the items (drug names / topics / units / question
   keywords) that are VISIBLY written in the image.
2. NEVER add, infer, guess, expand, or auto-complete any item that is
   not written in the image.
3. "Jo di hui vo drug hee, not think your side." — if it is not in the
   image, it does not exist for you.
4. If a word is unclear, do NOT guess it — omit it (or flag
   "unclear": true).
5. Ignore watermarks, page numbers, headers/footers, and logos.
6. Respond with JSON ONLY, no explanations:

{
  "source_type": "syllabus" | "question_paper" | "drug_list",
  "items": [
    {"name": "EXACT text as written in image",
     "type": "drug" | "topic" | "unit" | "question",
     "unclear": false}
  ]
}

7. If the image contains no readable text, return {"items": []}.

Prompt B — Per-Item Generation (point-wise bilingual notes)

# SYSTEM PROMPT (sent once per selected item)
You are a pharmacy exam-note writer for Hindi-medium B.Pharm students
(RUHS/PCI pattern).

You will receive ONE item name. Write notes ONLY for that item.

RULES (mandatory):
1. You MUST NOT write about anything other than the given item.
2. Never add related drugs, comparisons, or extra examples that were
   not asked. Stick to the item only.
3. Format: bullet points only. NO paragraphs. Maximum 12 points.
4. Each point: one line, simple English, exam-ready.
5. Points must be ordered: definition → mechanism → uses → side
   effects (if drug) — matching RUHS 2/5/10-mark answer style.
6. Respond with JSON ONLY:

{
  "item": "the item name you received",
  "points_en": ["..."],
  "points_hinglish": ["..."],  // same points, Roman Hindi +
                                // English medical terms, simple words
  "flowchart_steps": ["step1", "step2", ...]  // if a mechanism/life
                                // cycle exists; else empty array []
}

7. If the item is not a pharmacy concept you recognize, still write
   basic points from the term itself; do not refuse, do not invent
   unrelated content.

Prompt C — Validation guard (post-generation check)

# SYSTEM PROMPT (automated verification, no human needed)
You are a validator. You will receive:
- "image_items": the list extracted from the user's image (whitelist)
- "generated_titles": titles of notes the generator produced

For each generated title, check if it matches an image item
(exact match OR clear fuzzy match of the core term).

Return JSON:
{
  "kept":   ["titles that match image_items"],
  "rejected": ["titles NOT in image_items"]
}

Rule: any title with no match in image_items MUST go to "rejected".
The generator must never exceed the whitelist.
Why three layers? LLMs "hallucinate" — the model may correctly extract 5 drugs but then casually add "Paracetamol" to the notes. Layer B prevents it by prompt, Layer C catches it by checking the output against the whitelist. The validation result is also shown to the user as a trust badge: "✔ Verified: 5/5 notes match your image — koi extra item nahi joda gaya." That badge is your product's trust moat.

SECTION 10

Content Formatting Rules (the "No Paragraphs" Law)

Your rule is absolute — so it is enforced by the system, not by habit. Four enforcement layers:

Layer 1 · Schema

Content lives only in json[] columns. A paragraph physically cannot be stored as a single value — it must be split into array elements.

Layer 2 · AI prompt

Prompt B (§6.3) mandates "bullet points only, max 12, one line each, NO paragraphs" — every generated note obeys the rule at birth.

Layer 3 · QA validator

A scheduled check (Make.com monthly) scans all notes: any element > 200 chars or containing ". " multi-sentence chains → flagged for rewrite.

Layer 4 · UI

The renderer always displays points as bullet rows with spacing — even long content stays visually scannable; "copy" joins with "• ".

10.1 The 7-point content QA checklist (per note)

  • Point-wise: zero paragraphs; each point = one idea, one line (≤ ~25 words).
  • Flowchart present where the topic has a mechanism/life-cycle/process (MOA, ADME, synthesis steps, malaria cycle, gene transfer techniques).
  • Bilingual parity: en_points.length = hinglish_points.length; index n maps 1:1.
  • Simple-English rule: complex jargon first appears with its simple meaning, or links a glossary tooltip.
  • Exam structure: answer-type notes follow definition → mechanism → classification → uses → side effects; marks field set (2/5/10).
  • No invented content: (for scanner notes) title present in the image whitelist — validation log attached.
  • Tags & related: 2–5 tags + related-note links for "people also studied".
